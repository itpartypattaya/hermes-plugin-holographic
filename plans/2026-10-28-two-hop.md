# Two-hop links at query time — pre-registered experiment

Date: 2026-10-28. Base: `origin/main` c4be5c1. Branch `feat/two-hop-links`.
This file is committed BEFORE the dataset is run against any code. Nothing below may change after the first run
except the "Results" and "Decision" sections at the end (and the dev-only tuning log, which must say what changed).

## Question

Holographic recalls before each turn (prefetch) the facts that match the message's words, plus the top facts of
entities the message names. Every path makes ONE step from what the message says. A question whose answer sits one
entity further away ("Who is responsible for the server project Alpha runs on?" — the server is not named) gets the
first fact but not the second.

Option (b) of the relations research: walk entity co-occurrence (`fact_entities`) one step further at query time.
No new table, no LLM, no network, no stored inference.

## The prototype (fixed before the run)

A fourth recall stream, "hop", appended after the existing three, off/on by a config switch:

1. Seeds = the facts the block already holds (lexical + meaning + entity streams).
2. Missing terms = the message's informative terms (`query_terms`) that no seed contains (`found_in`).
   No missing term -> no hop at all (the block already covers the message).
3. Bridges = entities linked to the seeds, minus entities the message itself names, in the seeds' order.
   An entity linked to more than `HUB_CAP = 50` current facts is skipped (a hub: the user, the company).
   At most `HOP_BRIDGES = 3` bridges are walked.
4. Candidates = current facts linked to a bridge (the same `fact_entities` join `probe` uses, so forgotten,
   ended, merged and replaced versions are absent by construction; same `min_trust`), not already in the block.
5. A candidate qualifies only if it contains at least one missing term. Ranked by the IDF-free count of missing
   terms it covers, then trust. Same admissibility as every stream: `_recallable` (safety) and
   `prefetch_repeat_turns` de-dup.
6. At most `HOP_FACTS = 2` hop facts per turn. Each is shown as its own line with `#id [trust]` and "(via #seed)"
   — never a synthesized conclusion.
7. One store file only (scope = file); no cross-file walk.

## Dataset

Synthetic, invented names, no real people or family data. Two stores per run:

- `family`: ~300 facts (one fictional household, neighbours, school, doctors, clubs), Russian and English.
- `work`: ~2000 facts (fictional company: projects, services, servers, people, vendors), Russian and English;
  generated filler uses the same relation words as the questions ("responsible for", "отвечает за", "runs on",
  "работает на") so that a lone relation word is not a give-away.
- `work_other_chat`: a second store file (the chat/thread scope case) holding the far end of some chains.

Facts are written the way an agent writes them: `fact_store add` with `entities` for some facts, capitalised
names only for others; one-word names declared via `entities`. Changes go through `change`, `end`, `forget`.

40 questions (about half Russian, half English), each labelled with gold fact keys (all must be in the block),
forbidden keys (must never be in the block), and the type:

| Type | n | Gold | Forbidden |
|---|---|---|---|
| 2-hop, bridge not named in the question | 14 | both chain facts | — |
| 1-hop direct (control) | 8 | the answering fact | — |
| namesake trap (bridge is a one-word name two people share) | 4 | the right person's facts | — |
| changed / ended link on the path | 4 | the current chain (or nothing after `end`) | the old far end |
| forgotten fact on the path | 3 | nothing new | the forgotten fact and the far end reachable only through it |
| cross-scope (far end lives in another chat's file) | 3 | nothing new | every fact of the other file |
| no answer / inadmissible inference ("who pays for X" when only "works on" + "uses" exist) | 4 | nothing | — |

Held-out subset: every question whose index (0-based, in file order) is `i % 5 in {1, 3}` (40 %). Prototype
parameters may only be tuned on the other 60 % (dev); any tuning is logged below with the dev numbers that
motivated it. Held-out numbers are computed once after tuning stops.

## Modes

- `main`: the provider as on `origin/main` (rerank off, embeddings off — the defaults; no network).
- `hop`: the same provider with the hop stream on.

The runner calls the real provider: `HolographicMemoryProvider.initialize`, `handle_tool_call("fact_store", ...)`
for every write, `prefetch(question)` for recall; fact ids are parsed from the `- #id` lines. A fresh session per
question (no repeat suppression across questions). Not measured: an agent chaining `probe` calls (needs a model).

## Metrics

- Chain recall: share of questions whose gold facts are ALL in the block (2-hop set; also per type).
- 1-hop recall: same on 1-hop controls.
- Controls = 1-hop + namesake + no-answer/inadmissible (22 questions). On controls: irrelevant facts = injected
  minus gold (a wrong namesake's fact is irrelevant); noise share = irrelevant / injected; extra irrelevant per
  control question.
- Forbidden: count of forbidden facts injected (changed/ended, forgotten, cross-scope).
- Synthesized lines: any block line that is not `- #id [...]` (must be 0).
- Latency: prefetch wall time on the `work` store, every question 5 times; p95(hop) - p95(main).

## Adoption threshold (all must hold; else no feature PR)

- H1 chain recall on 2-hop questions: hop - main >= +20 pp, on all 2-hop questions AND on the held-out 2-hop subset.
- G1 1-hop recall: no loss (hop - main >= 0 pp).
- G2 controls: noise share hop - main <= +2 pp AND extra irrelevant facts <= 0.10 per control question.
- G3 forbidden facts injected by hop = 0 (and synthesized lines = 0).
  Clarified before the first run (second commit, still no result seen): the far end of a removed link is a current
  fact and may match the words of a question on its own; if `main` shows it too, the walk did not bring it. So G3
  counts (i) the removed facts themselves (forgotten, ended, other file) in the hop block — must be 0, and
  (ii) forbidden far-end facts in the hop block that the main block does not show — must be 0. Both are reported,
  and the strict count (every forbidden fact in the hop block) is reported alongside.
- G4 latency: p95 delta <= +20 ms on the ~2000-fact store.

On by default for the public only if, in addition, controls get 0 extra irrelevant facts on the held-out subset and
H1 >= +30 pp; otherwise the switch ships default off.

Next step (c, a typed relation table) is worth considering only if at least a third of hop's remaining 2-hop
misses are due to a missing relation type rather than a missing link — noted, not built here.

What not to build: LLM edge extraction, a Neo4j/graphify dependency, unbounded walks, walks across scope files,
synthesized "therefore" lines.
